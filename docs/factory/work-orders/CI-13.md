## Objective and fixed acceptance criteria

- Required GitHub check contexts must be the real, stable job names:
  - `sf07-portability (ubuntu-24.04, py3.12)`
  - `sf07-portability (windows-2022, py3.12)`
  - `sf07-acceptance`
- Add an `always()` acceptance job dependent on both individually named platform jobs (not an opaque matrix aggregate). Accept only if **both** `needs.*.result` values equal `success`. Failure, skip, neutral, cancellation, missing and unknown must not pass the acceptance expression. Its own job result must be `success`.
- All discovered Python tests in the mandatory suite must execute successfully, with zero unittest skips, expected failures or unexpected successes. Any skipped individual test is **unqualified** rather than silently waived; explicit future scoped exemptions require a separate work-order amendment/review and must not claim untested capabilities.
- Maintain a minimum baseline test count and a required critical-test inventory to flag unexpected test removal. These are anti-regression signals, not tamper-proof against edits to the gate itself.
- CI should record PR head/base; checked-out commit and tree; event type/ref; merge-group head/base (when present); workflow identity/run/attempt; and exact provider job ID, conclusion and source. PR-head and merge-group evidence remain separate.
- Do not require squash commit SHA == PR head or merge-group SHA. Qualify the final commit through provider merge relationships and exact tree/content correspondence where appropriate.

## Ruleset dependency and provider verification

The linked GitHub connector supports repository source, PR and CI operations, but no ruleset write operation. **Do not assert that the Base ruleset has changed until it has been successfully updated via an authorized UI/API and independently reread.** An operator may need to enable `required_status_checks` in https://github.com/spsoftwarefc/s-f/rules/24705576/edit and select the three contexts, with GitHub Actions as the expected source if available. Preserve the existing deletion, non-fast-forward, merge-queue and no-bypass settings.

The final activation gate requires bounded real hosted evidence:
1. Passing PR check on the final exact candidate (Linux + Windows + acceptance).
2. Passing `merge_group` check for the actual integration candidate.
3. An intentionally failing required-job candidate, plus missing/skipped/cancelled and superseded scenarios where safely testable. Never claim such provider behavior solely from mocked local unit tests. A passing queue candidate may auto-merge; use harmless, reviewable changes and the authorized merge boundary.
4. Independent observation that GitHub ruleset **requires** all three contexts, with correct source apps when supported.
5. Documentation reconciled to separate historical portability acceptance, prospective enforcement, and later SF packages. Close Issue #13 only when these acceptance proofs exist.

## Security/resource constraints

Existing pinned action SHAs, `contents: read`, no persisted checkout credentials, bounded 12-minute platform jobs, no secrets, no production hosts, no duplicate push event. Do not make reviewer approval mandatory. Record operator review of any changed instructions/tests/gates/workflows, including removed assertions, skips, soft failure handling, permissions, and action revisions. This review is procedural, not independent technical enforcement.

Develop and unit-test locally first; open one scoped PR, minimize hosted runs. No merge without completed checks, actual ruleset enforcement and explicit accepted boundary.
