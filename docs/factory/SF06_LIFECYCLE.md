# SF-06 lifecycle contracts

Status: development preview. Integration, upgrade and removal are opt-in filesystem operations for an authorized local developer. They do not run project commands, change CI, merge, or deploy.

## CLI

- `sf integrate --dry-run --root PATH --profile PROFILE` builds a read-only plan.
- `sf integrate --apply PLAN --root PATH --profile PROFILE` applies an exact revalidated plan.
- `sf upgrade --dry-run --root PATH --profile NEW_PROFILE` previews an upgrade.
- `sf upgrade --apply PLAN --root PATH --profile NEW_PROFILE` applies it.
- `sf remove --dry-run --root PATH` previews removal.
- `sf remove --apply PLAN --root PATH` removes only verified factory-owned files.
- `sf recover --root PATH` verifies and resumes an interrupted operation.

For projects with existing AGENTS.md, `--ack-manual-routing` on the integrate dry-run and apply preserves the existing file byte-for-byte and records that manual instruction integration is still needed.

## Contract and authority

A plan document is not a write authorization. Apply requires a separate explicit command. The system re-evaluates the project root, validated profile, known factory path list, existing state and content digests. A saved plan that differs from the fresh derived plan is rejected. A new installation writes only the generated .s-f namespace and an AGENTS.md routing stub when the latter did not exist. Existing custom CI, project files and instructions are preserved.

The lifecycle plan contains the mode, root, old/new profiles, ownership route, ordered before/local/after evidence, conflicts and a no-release-qualification indicator. Current Git state and CI enforcement are not attested by this plan. Exit 0 indicates completion/no-op, 1 an unresolved dry-run conflict, and 2 invalid prerequisites or an execution error. An execution error is NOT evidence of rollback.

## Recovery

Before target mutation, the runner creates and syncs a single local transaction journal, .s-f-transaction.json. After each exact-byte precondition check, it uses same-directory staged file replacement or deletes only a known owned file; the ownership manifest is finalized last. On POSIX it syncs written files and parent directories. Successful completion removes the journal.

Recovery validates the journal against the factory's built-in generated effects and old/new validated profiles. Every target must match its original or desired bytes before processing resumes. A modified target, forged path or malformed journal causes a safe block. Replayed completed steps are skipped. This is checked roll-forward, not atomic multi-file rollback. Incomplete or corrupt journals require operator review and must not be blindly ignored.

## Upgrade and removal

Upgrade compares installed base, local bytes, and desired generated bytes. A local modification that differs from both expected states is retained and reported as a blocking conflict. Automatic textual merging of policy and agent instructions is deliberately excluded. Repeat application, repeat upgrade and repeat removal are no-ops once the desired state is reached.

Removal validates the ownership manifest and removes only byte-matching owned paths. Unrelated project data, CI, CLAUDE.md and a preexisting project-owned AGENTS.md remain untouched. Factory directory removal occurs only when empty.

## Limits and qualification

The journal is local project state, not a cryptographic attestation. Hostile concurrent filesystem writers, multi-process locking, unsigned factory distribution, Windows durability semantics and platform isolation remain unqualified in this implementation. The local runner is not a sandbox. Cross-platform portability and end-to-end acceptance belong to SF-07 (PR #12); actual developer execution/CI and release qualifications belong to later packages.

## SF-13I pinned portable installation (development candidate)

Normal `sf integrate` and `sf upgrade` now require `--bundle ZIP`, `--trust APPROVED_PIN_JSON` and `--lock FACTORY_LOCK_JSON` during dry-run and apply. The operator must authenticate and protect the release pin through a channel independent of the archive. `sf recover` requires these same original inputs when resuming a bound transaction.

An exact verified source payload is written without decoding under `.s-f/portable/<bundle-member-path>`. The qualified path records `.s-f/FACTORY_LOCK.json` and binds every installed member in `.s-f/OWNERSHIP.json`. The generated profile, routing and ownership files are target-specific output, and are not claimed to be ZIP member bytes.

Read-only plans do not change the project. Apply revalidates the archive, independent pin, canonical lock and exact saved plan; it journals desired bytes before target effects, checks conflicts on every step, and commits ownership last. Recovery rejects changed locks and forged journal steps. Foreign files and existing custom instructions remain owned by the project.

An explicit `--development-preview-unpinned` switch permits the earlier unqualified lifecycle for backwards compatibility. Direct calls to legacy Python preview operations also remain possible. Neither route is a qualified distribution-installation path.

**This is an implementation candidate, not a production claim.** It still needs exact-candidate Linux/Windows test evidence and substantive review. Local lock matching does not attest who created/provisioned the external trust pin, and the verifier has no publisher-signature verification.
